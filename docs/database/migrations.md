# LeadSynt — Database Migrations

**Rule: schema changes only via Alembic. No `create_all`, no hand SQL, no
ORM-driven auto-migration in app code.**

## Stack

- `backend/alembic/` — env wired to `app.core.config`'s DB URL (env-driven).
- `backend/alembic/versions/ed1b5a8cff29_initial_schema.py` — foundation schema (46 tables), autogenerated from the SQLAlchemy 2.0 models and then reviewed.

## Commands (from `backend/`, venv active)

```bash
alembic upgrade head        # apply all migrations
alembic current             # show current revision
alembic downgrade -1        # roll back one revision
alembic revision -m "add x" # create a new empty revision
alembic revision --autogenerate -m "add x"   # draft from model diff
```

## Workflow for a new change

1. Change the SQLAlchemy model(s) in `app/models/`.
2. `alembic revision --autogenerate -m "describe change"`.
3. **Read the generated file.** Fix anything autogenerate gets wrong on
   SQL Server (index naming, enum handling, default expressions).
4. `alembic upgrade head` on a **copy** of the dev DB first.
5. Run the full test suite (`pytest app/tests -q`) — the in-memory SQLite
   fixture runs migrations against the same models.
6. Commit model + revision together.

## Notes

- SQLite does not create parent directories for the DB file — ensure
  `database/dev/` exists (or use a relative path with an existing dir).
- The dev profile uses the identical models on SQLite, so a migration that
  works on SQLite is a strong (not sufficient) signal for SQL Server —
  always verify `mssql+pyodbc` before shipping.
- The initial revision contains explicit `server_default` values for all
  status/type enums so raw SQL inserts are safe.
